# Operations

All commands use `./codex-infra COMMAND --private /absolute/private/directory`. That directory must be outside the clone. Run `plan` before applying locally; the plan and raw ARM preview remain private. The CLI exposes `bootstrap`, `adopt`, `plan`, `apply`, `verify`, `rollback`, and `rotate-credentials`. `bootstrap --fresh` creates a fresh VM after privileged setup. Bootstrap and adoption are administrator operations; routine deployment uses the workload principal.

`apply` reads actual infrastructure and managed host files, calculates differences, uses the scheduled daily VM backup for terminal-image-only updates and completes an additional VM backup before other disruptive changes, retains previous runtime configuration and applies only changed components. No-op applications do not rotate credentials, recreate containers or rewrite equivalent configuration. The applied Git commit, lockfile and private configuration fingerprint are stored root-only on the VM. Scheduling runs verification, never automatic adoption of drift.

Keep source branches current with main and prefer no-reply author and committer emails. The owner-approved address in `tools/privacy.py` is also permitted. GitHub's web rebase merge rewrites committer metadata using the merging account; it is suitable when that account's GitHub commit email is no-reply or explicitly allowed by the privacy scanner. See the procedure below when keeping account settings unchanged.

The production workflow uses a non-cancelling concurrency group with GitHub's buffered queue, so scheduled verification cannot replace a pending deployment. When it obtains the lock it checks out current `main` and runs validation and container tests against that actual revision. A queued old workflow therefore reconciles the latest desired revision. No PR, fork PR or feature branch can enter the production environment or obtain its Azure identity.

## Merging with account settings unchanged

An explicitly authorized administrator merge can fast-forward the exact checked PR head without generating new commit metadata. This is a merge operation, separate from deployment; bootstrap and apply never merge PRs or relax branch protection.

1. Confirm the PR is reviewed, current with main and all required checks passed on its exact head. Fetch both refs in a clean clone, run the privacy/history scan and record the reviewed head and current main SHA privately. `git merge-base --is-ancestor origin/main REVIEWED_HEAD` must succeed.
2. First attempt an ordinary fast-forward push with all protections unchanged: `git push origin REVIEWED_HEAD:refs/heads/main`. GitHub can accept the exact head of an existing PR that satisfies its required checks and review rules. Never use force. A changed main or failed check requires re-review.
3. If GitHub rejects that push because a pull-request bypass is required, stop. Named bypass lists are available only on organization-owned repositories; do not attempt to configure one on a personal repository. An organization administrator may save the protection configuration privately, temporarily grant only the named merging administrator a pull-request bypass, and retry the same checked fast-forward. Keep required checks, strict freshness, linear history and force-push/deletion restrictions enabled.
4. If a temporary organization bypass was used, restore the exact prior configuration immediately, including after a failed push. Verify the PR is marked merged, main points to the reviewed commit and production CI starts. Retain the protection record privately.

This preserves both source author and committer emails and triggers the ordinary main-push deployment. If you cannot obtain a narrowly scoped administrator bypass, leave the PR unmerged until an authorized merger with a no-reply GitHub commit identity is available. Never silently accept personal commit metadata or disable the privacy check to deploy.

## Image updates

The **Update terminal image** workflow checks GHCR daily at **02:23 UTC**, on manual dispatch, and when the updater itself changes on main. GitHub schedules can be delayed. It resolves upstream `latest` to an immutable SHA256 digest, verifies the registry manifest and Linux AMD64 support, and changes only `terminal` in `images.lock.json`.

The updater opens a bot PR and explicitly dispatches the read-only **Validate** workflow on its exact head. Both `validate` and `container-policies` must succeed. GitHub does not count workflow-dispatch job checks toward PR merge requirements, so the trusted main updater reports their verified results as commit statuses on that exact candidate SHA. It sets both required contexts pending first, publishes success only after the entire workflow and both jobs succeed, and reports failure/error when validation fails or cannot complete. Status links point to the validation run. Only the updater has `statuses: write`; candidate validation remains read-only. This preserves required checks without a PAT, extra app, or branch-protection changes. It rechecks the PR author, repository, head, base and single-file contents, then rebase-merges with all branch protections unchanged. It explicitly dispatches **Production** on main with `reconcile=true`, because a merge made with `GITHUB_TOKEN` does not trigger the ordinary push workflow. No PAT or additional secret is needed. Manual Production dispatch still defaults to verification only; select `reconcile` to apply first. The existing 05:17 UTC production schedule remains verification only.

Bootstrap enables **Settings → Actions → General → Workflow permissions → Allow GitHub Actions to create and approve pull requests**, while retaining read-only default permissions. Existing installations must enable that checkbox once. The updater does not submit approving reviews or bypass checks. GitHub's repository-level auto-merge option is not required; the workflow merges only after validation succeeds.

A failed candidate stays open for investigation. To retry the same candidate, fix or rerun its dispatched Validate run, then run **Update terminal image** again. If main or the upstream digest advances, a new branch based on current main replaces the old bot PR. Branches are never force-pushed and human-created PRs are left alone. A missing deployment dispatch after a successful bot merge is recovered on the next updater run; an active or successful production run for that revision is not duplicated. Failed production runs remain visible in Actions and may be retried on the next updater run. Deployment verification failure still invokes the existing runtime rollback; Git/image rollback does not restore workspace data.

Automatic updates can interrupt terminal sessions during the deployment window. To pause image discovery, disable **Update terminal image** in Actions. Deployment or compatibility fixes continue through ordinary reviewed PRs.

Edit only the relevant digest in `images.lock.json` on a feature branch, validate, and open a pull request. Terminal-image-only updates skip the on-demand backup and rely on the daily seven-day VM backup policy. Any simultaneous infrastructure, callback, container-limit, mount, other-image or host-configuration change retains the pre-change backup requirement. Runtime rollback still preserves the previous image and configuration; data recovery can lose changes since the last daily backup. Tags and `latest` are rejected. The three images and the OS image version are separately pinned. Pull images before mutation. An update confined to the terminal digest recreates only the terminal container. The authentication and HTTPS container IDs must remain unchanged. Verification exercises native PTY/WebSocket access, same-origin checks, sandbox write allow/deny, persisted mounts and saved Codex authentication.

OS image version changes require an explicit replacement/recovery procedure; an automatic deployment refuses immutable VM changes. Updating the lockfile does not silently reimage an existing VM.

## Domains and resizing

Manage domain registration and DNS with your provider. Point an A record for the chosen hostname to the deployment's private recorded public IP (or a supported CNAME to its Azure hostname). Update `hostname` only in the private configuration and republish the environment secret using bootstrap. `plan` validates the change; `apply` adds the new Entra callback, updates only the affected authentication/TLS configuration, verifies public TLS and redirects, and removes the old callback. Failure restores the previous runtime configuration and callbacks. Never put your domain or DNS provider credentials in Git.

VM size and container limits are public settings in the selected profile. Keep B1ms during adoption. A later size change needs its own reviewed maintenance change. Apply completes a backup, deallocates the VM, updates its size and starts it again; a failed resize restores the previous size and starts it. Resizing interrupts active sessions. Automatic reconciliation must not replace the VM or change disk/IP identity to satisfy a size request.

## Credentials

Ordinary apply and adoption preserve both client and cookie secrets. `rotate-credentials` is an explicit administrator operation: create a replacement client credential, back up, update only authentication, verify access, upload the replacement to the environment and only then revoke the mapped old credential. The cookie key is preserved. On failure the old credential remains valid and a root-only/local pending recovery record identifies the replacement. Entra interactive sign-in should be checked after rotation; unattended health checks cannot prove a human's complete MFA browser experience. Never guess which historic credential is active or delete unmapped credentials.

Update your encrypted recovery copy whenever private settings or credentials change. Credentials expire; schedule rotation before their recorded expiry. Do not add an automatic rotate step to a no-op deployment.

## Rollback and interrupted deployment

Runtime verification failure restores the previous configuration and images. It never restores an old workspace snapshot. `rollback` explicitly selects the last recorded runtime revision (or `--revision` from private state), after completing a backup. Explicit rollback preserves the currently active client/cookie credentials so a previous rotation's revoked credential is not reinstated. Revert the corresponding repository commit through a pull request so the desired configuration agrees with the rollback. A pending host transaction stops the next apply and requires recovery; never erase it to force an update.

Infrastructure reconciliation is incremental and refuses deletion and immutable VM changes. Infrastructure failures are not automatically reversed through destructive ARM deployment. Resolve the private preview and recover explicitly. No automatic path permanently deletes data, workspaces or backups.

The host retains the configured number of private runtime revisions. VM recovery points use the configured daily retention; service-managed snapshot and backup artifacts follow Azure Backup policy. The controller reuses one owned Managed Run Command resource to respect Azure's 25-resource-per-VM limit, and each invocation has a unique completion marker to reject stale results. Only other managed Run Command records older than the configured retention are removed automatically; records outside the managed prefix remain for the administrator to review. Never use Docker image pruning as part of deployment: offline rollback needs the previous image.

## Terminal restoration

The read-only Node helper wraps the upstream launcher without changing its image. It rebuilds tmux's `main` session before Remobi starts, restoring window names/order, split layout, pane directories, the selected window/pane and zoom. The persistent Codex-config volume holds owner-only, versioned JSON checkpoints under `terminal-restore/`. Checkpoints are written atomically every five seconds and frozen before replacement; they contain directories and conversation IDs, never terminal output or arbitrary shell commands. Deployment logs omit their contents. Verification does not invoke restoration or write checkpoints.

Managed `SessionStart` and `SessionEnd` hooks associate the exact conversation with its tmux pane and live Codex process. The helper and `/etc/codex/requirements.toml` are read-only management mounts; user hooks, authentication and configuration remain intact. After the first installation, reopen each existing conversation once so the hooks can track it. The first rollout can recover the terminal layout but cannot infer conversation IDs from already-running Codex instances.

Every automatic resume, including rollback, runs `codex resume --dangerously-bypass-approvals-and-sandbox SESSION_ID` without a continuation prompt. This is YOLO mode: Codex approvals and its inner sandbox are bypassed for that restored conversation. Global defaults and manual launches are unchanged. Container security boundaries, authentication, TLS, WebSocket and origin checks remain enforced. Processes and in-flight commands stop during replacement. Reload or reconnect the browser if needed.

Only explicitly mapped active conversations resume, and duplicate IDs resume once. Missing directories fall back to `/workspace`; a failed resume prints a local notice and opens a shell. Missing/invalid checkpoints open a fresh terminal. A valid deployment checkpoint survives failed startup and rollback until host and public access checks succeed. Repeated startup against an existing `main` session does not replay resumes. A rollback to a release predating this helper necessarily returns to that release's manual reopening behavior.

Roll out through the feature PR and required Validate checks. After installation and the one-time reopen, replace only the terminal container and check window names, splits, directories, selection and exact conversation mappings. Confirm restored Codex waits for input in YOLO mode, and auth/HTTPS container IDs are unchanged.

Long pre-change backups refresh the GitHub workload login every five minutes and once more before follow-up deployment operations. Each refresh obtains a new GitHub assertion for the existing production identity; no stored client secret or identity-policy change is needed. The main-only **Production diagnostics** workflow reads backup/deployment states without acquiring the mutation lock or invoking host commands. It also verifies the refreshed identity and outputs only bounded public states, timestamps and machine error codes.
