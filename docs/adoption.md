# Adopt an existing deployment

Adoption must preserve the VM instance, managed disk, static public IP, custom hostname, runtime application/service principal, workspace and backup policies. Keep B1ms and existing retention settings. No service restart, credential rotation, workspace migration, resize or VM/disk replacement is allowed in the first adoption.

1. Securely retain the old private configuration, state and administrator key. Do not copy the old checkout, `.azure` directory, Git history or generated configuration into this repository. Create a separate mode-0700 directory outside the new clone.
2. Inventory resource IDs/names, VM instance ID, disk ID, public IP resource/value, subnet, image digests, runtime app/client/service-principal IDs, allowed user object ID, budget scope/start date and recovery resources. Write only those private mappings to `private.json`, using `schemas/private.schema.json`. Use profile `adopted`, with all optional modules enabled in `config/adopted.json`. Map `resources.recoveryStorageName` and `resources.auditWorkspaceName`; preserve the existing `budgetResourceGroups` list. Map `hostname` and `azureHostname` separately. Preserve the original administrator public key.
3. In `credential-mapping.json` privately record `{"keyId": "<active runtime credential key ID>"}` from the existing state. Never guess between multiple app credentials. Adoption can import secrets without a key mapping, but credential rotation is prohibited until that mapping is established.
4. Review the public lockfile and infrastructure against the inventoried deployment. Run `bootstrap` without `--fresh`. It creates the scoped deployment identity, grants owned-runtime access and live MFA policy read, and uploads private configuration to the restricted production environment. Bootstrap never configures or restarts the existing host.
5. Run `adopt`. The CLI obtains the runtime client and cookie secrets through a one-time CMS-encrypted VM-to-local transfer using a temporary local recipient key. Azure sees protected parameters and ciphertext output; no rendered proxy file is exported. Plaintext exists only in memory and in the mode-0600 local recovery file and encrypted GitHub secret. The temporary transfer key is destroyed after import.
6. The command compares actual infrastructure and managed host files with repository-defined configuration, checks live access policy and public redirects, and refuses adoption if any functional change is needed. It records a root-only applied revision and a local immutable resource baseline and verifies that container IDs did not change. A mismatch must be resolved by correcting the repository or private mapping; do not bypass the no-op requirement.
7. Reapply unchanged configuration and run `verify`. Confirm the original VM instance, disk, IP, domain and containers are unchanged and owner access continues. Keep private baseline records and an encrypted recovery copy. Complete the fresh-clone and isolated backup/restore tests before retiring old deployment tooling.

Changing tags or adding private management records is permitted. Adopting a deployment with different resource names or settings requires an explicit reviewed mapping/template change. Do not rename or replace resources to make the template fit.

After migration and recovery validation, update the existing fork's documentation and upstream deployment-guide PR to point here. Remove duplicate public infrastructure code through a reviewed follow-up so there is a single maintained implementation. Retain the old **private** deployment files securely until recovery validation is complete.
